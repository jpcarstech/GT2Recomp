# Framework patches carried by GT2Recomp

Minimal bugfix patches applied on top of the pinned `psxrecomp` submodule.
Pins (2026-09-01 rebase): `psxrecomp` = `afe9ab29` (the commit Alexbeav's
Wave 2 v0.3.0 kits were qualified on; brings the GTE conformance fixes, the
30 Hz elided-swap pacing fix, sliced GPU linked-list DMA, and upstream's
title-scoped exact NCLIP), `recomp-ui` = `4eda6543`. Retired at that rebase
because upstream now carries them: `zzzzz-pgxp-sxy-shadow-validation`
(322543c2), `zzzzzzz-gte-read-helper-classification` (fff63301), and the
NCLIP arbitration pair `zzzzzzzzzm`/`zzzzzzzzzn` (folded into
`zzzz-pgxp-precision`, see below).
Policy: no feature deviations from upstream — entries here are defects we
intend to upstream, and each disappears once merged.

Applied by `tools-win/local-build/local_build.sh` (and checked by CI) in this order: `patches/upstream/*.patch`, then `patches/psxrecomp-*.patch`, both sorted with `LC_ALL=C`; then `patches/recomp-ui/*.patch` onto `recomp-ui/`. Order matters - later carried patches build on earlier ones.

| `psxrecomp-zzzz-pgxp-precision.patch` (scale caps) | **The reason supersampling above 4x never took effect.** Two stale limits survived the 16x raise, in two different repos, and both failed silently. (1) `gpu_gl_renderer.c` carried a private `GL_MAX_INTERNAL_SCALE 4` that shadowed the shared `PSX_GL_MAX_INTERNAL_SCALE 16` from `gpu_sw_renderer.h` (which the file already includes); both config load paths accept 1..16 and main.cpp passes the value through untouched, so the launcher could offer 6/8/12/16, settings.toml stored the choice, and `glb_set_scale` quietly reduced it to 4. (2) recomp-ui's `launcher_model_load` normalised supersampling with `clampi(..., 1, 4)` while the cycle and label functions immediately below it use 1..16 - so a settings.toml carrying 12 was reduced to 4 on load AND written back over the user's choice. Net effect for anyone on a high-DPI display: a 4K user selecting 12x rendered at 1280x960 internally, upscaled ~2.2x to screen, with every one-pixel seam magnified - and no error anywhere to explain it. Verified end to end: `internal scale 4x` before, `internal scale 12x` after, hires buffer 1280x960 -> 7680x5760. **Whole-primitive completion now defaults OFF - it corrupts 2D.** Its 3D proof was that all three corners coincide with recorded GTE projections, which CPU-authored 2D should never do; that held in the lab but not in the field, where the census came back `native2d = 0` with `whole_done = 2880` (every fully-native primitive completed, UI included) and the pause menu rendered with skewed plates and seams down the edges - exactly the failure that forces DuckStation's vertex cache off. It also never bought anything visible: a deterministic static frame measured ZERO pixel change, because the polygons it recovers are far-LOD micro-triangles. A correctness metric that improves while the picture degrades is not a win. Still available via `pgxp {"whole":1}`. The crack detector's three parameters (draw-order threshold, flank-similarity tolerance, fill radius) are also live-tunable now via `pgxp gfthr/gfsim/gfrad` and `pgxp_tune`, since sweeping them previously needed a rebuild per guess. **Coverage target capped for high internal scales.** At 16x the 1:1 coverage target is 16384x8192 R8 on top of ~1.5GB of colour/depth surfaces - enough to hit a GPU dimension limit or simply fail to allocate - and the failure path disabled the ENTIRE crack fill, visualiser included, with no message. On the reporting machine every fill mode became a no-op the moment they moved to 16x. Dimensions are now capped at 8192 and sampled through a divisor (the pass emits NDC, so a smaller viewport rasterises the same geometry into the smaller target; the present shader divides its lookups to match). A crack is ~1 native pixel = s_scale hires pixels, so even a 4x reduction leaves several coverage texels across it. Retries once smaller, and if it still fails it says so and names the remedy. Verified at 16x: allocates 8192x4096, fill reports active. `pgxp` also reports `gf_why` (bitmask of the four preconditions the present path checks) and `gf_active`, so a silent drop can never again cost a round trip to localise. **Crack detection reworked from coverage to DRAW ORDER.** The user's coverage visualiser settled a long-running failure: the ENTIRE 3D scene reads as covered, magenta only on HUD text and the tachometer - so the crack fill was a no-op everywhere in the world, in every mode, which is why gapfill 0..3 looked identical. The definition was wrong: it looked for pixels where NOTHING drew, but GT2 paints back-to-front, so a crack between two terrain polygons still has the backdrop drawn in it. Their fullscreen capture shows it plainly - cyan sea tracing the polygon edges of the ground mesh, median run 8 screen px, 70% with matching surfaces on both flanks. Mode 3 now stamps a per-primitive draw ordinal (normalised against the previous frame's primitive count, so the 8-bit target spreads its buckets over the real submission count rather than saturating) and a crack becomes a thin run drawn EARLIER than the surfaces flanking it - background-through-foreground under a painter's algorithm - guarded by requiring the two flanks to resemble each other so a narrow strip of background between two DIFFERENT objects is left alone. The mode-2 visualiser shows the ordinal as a ramp (magenta never drawn, blue early, red late). Lab-verified that the buffer goes from 1 distinct level to 45 in-race; NOT verified against the reported artifact, which the lab scene does not exhibit. The `pgxp` debug reply also now reports perspective-texture correction, the gap-fill mode, whole-primitive completion and the EFFECTIVE internal scale - all four were runtime state with no read-back, which is precisely how a clamped scale hid behind a settings file that claimed otherwise. Both caps now reference the shared constant; a clamp is reported instead of applied silently; and because raising the cap makes oversized requests reachable, `init_gpu_raster` now fits the scale to the GPU's `GL_MAX_TEXTURE_SIZE`/`GL_MAX_RENDERBUFFER_SIZE` BEFORE allocating - previously an over-ambitious scale failed deep inside init and dropped the whole GL pipeline to the software renderer. |

| `psxrecomp-z-gp0-unknown-nop.patch` | Unknown/undocumented GP0 opcodes were a fatal halt — one stray word crashed the run to desktop (GT2's race-start camera fly-in emitted word `0xF90C0C66`, opcode 0xF9). Real hardware ignores these words (psx-spx: unused opcodes act as NOPs), and DuckStation and Beetle skip them the same way. Now consumed as a NOP, with the first 8 occurrences logged to stderr together with the recent GP0 ring tail (frame, opcode, source addr, guest func/ra) so a genuine display-list desync — the only thing the halt ever caught — stays diagnosable instead of taking the player down with it. |
| `psxrecomp-zz-dma-ll-end-marker.patch` | GPU linked-list DMA only recognized the exact `FFFFFFh` end marker. Per psx-spx, ANY next-pointer outside the 8 MB DRAM decode window stops the transfer with a DMA bus error (DICR bit 15, forcing bit 31) — and some games end chains by toggling the high bit deliberately. We masked such pointers back into RAM and kept walking garbage until the 256k-node safety cap, twice per transfer (main walk + widescreen prepass), so one corrupt/high-bit OT tag became tens of millions of bogus GP0 words per frame — GT2's race start froze the host for seconds per frame ("application is not responding"). Now the walk stops there, DICR bit 15 is flagged through the existing master-edge IRQ latch, and hitting the safety cap itself warns (rate-limited) instead of truncating silently. **Post-rebase:** ported onto upstream's sliced linked-list walker (`dma_gpu_ll.c`, 8af48ae9): `next_is_bus_error()` stops the state machine, `gpu_ll_complete()` raises DICR bit 15 / sets MADR to the offending pointer and reports the MAX_NODES truncation. |
| `psxrecomp-zzz-gp0-irq-and-aperture.patch` | Two follow-ups from the same GT2 race-start investigation. (1) GP0(1Fh) Interrupt Request is a DEFINED command (sets GPUSTAT bit 24, raises IRQ1, edge-held until GP1(02h) acks) but sat on the unimplemented-fatal path — a stray 0x1F word in a corrupt display list took the whole process down where hardware just latches an interrupt; with it implemented, every GP0 opcode now has defined behavior and the unimplemented halt is unreachable. (2) The new linked-list bus-error stop must not fire for pointers into the allocated mod GPU-DMA aperture (0xF00000+, deliberately placed above the 8 MB window so trusted-enhancement pointers survive tag truncation): resolve first, and only raise the bus error when the address actually folds. **Post-rebase:** the aperture exemption lives in `dma_gpu_ll.c next_is_bus_error()` (resolve first; bus error only when the address actually folds) and the `gpu_ws_prepass_linked_list` mirror. |

| `psxrecomp-zzz-verify-trust-persist.patch` | The differential-verify budget (32 consecutive clean native-vs-interpreter passes before a shard may run native-live) lived only in-process, so EVERY launch re-verified every hot candidate from zero — running each dispatch twice for the first minutes of play. On a warmed cache that is a large recurring startup tax (GT2: ~15k candidates; the intro movie audibly starved the audio thread every launch, and native share needed minutes to climb). A shard's verification outcome is a function of its compiled bytes, not of the session: completed identities (entry addr, authoritative code CRC, compiler tier) persist to `verify_trust_v1.txt` under the cache; matching candidates register pre-trusted. Diverging candidates reset their budget and can never complete it, so they are never persisted; a recompiled shard has a new CRC, so stale trust cannot apply. |
| `psxrecomp-zzz-semi-batch.patch` | Every semi-transparent textured prim flushed the open batch and drew in its own isolated GL call — on GT2 races (shadows, fences, glass, smoke) that made ~395 draw batches per ~1,500-prim frame (~9 µs/prim, GPU draw-call bound, frame-time spikes past budget = hitching). The dual-source path (modes 0/1/3, mask-check off) composites each fragment in ONE ordered pass, and GL rasterizes a draw's primitives in submission order — so runs of such prims now batch. Opaque keeps its own batch key, so opaque↔semi transitions still flush in submission order; the CTR ordering bug the isolation was added for came from coalescing opaque INTO the dual-source key, which remains prevented. A second, independent bug compounded it: `wide_target_end` only restores the color program's x-projection uniforms, not GL viewport/scissor, so the canonical coverage pass immediately after a wide-mirrored batch was drawing with the wide surface's viewport/scissor still active - corrupting 4:3 coverage too on any frame that used the wide mirror.
